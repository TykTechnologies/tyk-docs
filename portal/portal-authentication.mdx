When an API Consumer is granted access to an API Product they will be issued a credential (for example an Auth Token) to present in the API request. For this reason, an API Product can only contain APIs that use a common [authentication method](/portal/api-products#authentication-method).

This page summarises which methods the Portal supports, what API Consumers and API Owners can do with each, and which types can be combined.

<Note>
This page covers authentication methods from the perspective of the Developer Portal. For configuration of client authentication at the Tyk Gateway-level, see [API Authentication](/api-management/client-authentication).
</Note>

## Credential Management: Self-Serve vs Managed

The Portal supports two methods for credential issuance and management:

**Self-Serve:** The API Consumer creates, rotates, and revokes their own credentials from the Live Portal.

**Managed:** The API Owner manages the creation and rotation of credentials. API Consumers have view-only access, or can revoke but not create or rotate credentials.

The **Mode** column in the table below indicates which model applies to each authentication type.

## Supported Authentication Types

| Auth Type | Mode |
|---|---|
| [**Auth Token / API Key**](/api-management/authentication/bearer-token) | Self-Serve |
| [**JWT / OAuth**](/basic-config-and-security/security/authentication-authorization/json-web-tokens) | Self-Serve |
| [**Auth Token + mTLS**](/api-management/implement-tls#using-a-static-client-certificate-allow-list) | Self-Serve or Managed |
| [**JWT + mTLS**](/api-management/implement-tls#using-a-static-client-certificate-allow-list) | Self-Serve or Managed |
| [**Basic Authentication**](/api-management/authentication/basic-authentication) | Managed |
| [**Custom Authentication**](/api-management/authentication/custom-auth) | Managed |

### Unsupported Authentication Types

APIs secured with [HMAC](/basic-config-and-security/security/authentication-authorization/hmac-signatures), [Tyk OAuth 2.0](/api-management/authentication/oauth-2), [Certificate Auth](/api-management/authentication/certificate-auth) or the deprecated [OpenID Connect (OIDC)](/api-management/client-authentication#integrate-with-openid-connect-deprecated) and [External OAuth](/api-management/client-authentication#integrate-with-external-authorization-server-deprecated) methods are not supported by the Portal and cannot be included in API Products.

[Open](/basic-config-and-security/security/authentication-authorization/open-keyless) (unsecured or keyless) APIs with no client authentication are also not supported.

## Dynamic Client Registration (DCR) for OAuth 2.0

When an API Product grants access to APIs secured using JSON Web Tokens (JWT), the tokens are issued by external Identity Providers (IdPs).

When an API Consumer requests access for their developer app, the Portal uses [Dynamic Client Registration (DCR)](/tyk-stack/tyk-developer-portal/enterprise-developer-portal/api-access/dynamic-client-registration) to automatically register an OAuth 2.0 client with the IdP on their behalf, returning a `client_id` and `client_secret` to the developer. The API Consumer then uses those credentials to obtain a JWT from the IdP, which they present to the Tyk Gateway. Tyk validates the JWT and creates a [Session](/api-management/access-control/overview#2-dynamically-generated-sessions) dynamically. No pre-registration with Tyk is required.

This differs from the [Authentication Token](/api-management/authentication/bearer-token) method, where Tyk issues the access token directly.

<Note>
The Tyk OAuth 2.0 authentication method, which uses Tyk as the auth server, is not supported by the Developer Portal.
</Note>

### Supported Identity Providers

| Identity Provider | Support | Notes |
|---|---|---|
| Keycloak | Fully supported | N/A |
| Okta | Fully supported | Requires the `OktaAppType` field (`web`, `native`, `browser`, or `service`). For Client Credentials flow, set the allowed response type to `token` only. |
| Gluu | Fully supported | N/A |
| Curity | Supported via Other type | Curity requires authentication on its DCR endpoint by default. Workaround: disable DCR endpoint authentication in Curity (no-authentication mode). |
| Any RFC-compliant IdP | Supported via Other type | Select **Other** in the DCR template settings. Full compatibility is not guaranteed. |

## Interactive Documentation and Playground Authentication

The Portal automatically handles authentication when Consumers use interactive API documentation or testing interfaces.
