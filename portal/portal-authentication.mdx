## Credential Management: Self-Serve vs Managed

Credentials can be owned by the API Consumer or by the API Owner:

**Self-Serve:** The API Consumer creates, rotates, and revokes their own credentials from the Live Portal.

**Managed:** The API Owner creates and rotates the credentials. The API Consumer can view and revoke them, but can't create or rotate them.

The table below shows which mode applies to each authentication type.

## Supported Authentication Types

| Auth Type | Mode |
|---|---|
| [**Auth Token / API Key**](/api-management/authentication/bearer-token) | Self-Serve |
| [**JWT / OAuth**](/basic-config-and-security/security/authentication-authorization/json-web-tokens) | Self-Serve |
| [**Auth Token + mTLS**](/api-management/implement-tls#using-a-static-client-certificate-allow-list) | Self-Serve or Managed |
| [**JWT + mTLS**](/api-management/implement-tls#using-a-static-client-certificate-allow-list) | Self-Serve or Managed |
| [**Basic Authentication**](/api-management/authentication/basic-authentication) | Managed |
| [**Custom Authentication**](/api-management/authentication/custom-auth) | Managed |

### Unsupported Authentication Types

| Auth Type | Reason |
|---|---|
| [**Certificate Auth**](/api-management/authentication/certificate-auth) (standalone) | mTLS only works combined with an Auth Token or JWT, as shown in the table above |
| [**HMAC**](/basic-config-and-security/security/authentication-authorization/hmac-signatures) | Not supported |
| [**Tyk OAuth 2.0**](/api-management/authentication/oauth-2) | Tyk itself acts as the authorization server |
| [**OpenID Connect (OIDC)**](/api-management/client-authentication#integrate-with-openid-connect-deprecated) | Deprecated |
| [**External OAuth**](/api-management/client-authentication#integrate-with-external-authorization-server-deprecated) | Deprecated |
| [**Open (Keyless)**](/basic-config-and-security/security/authentication-authorization/open-keyless) | Not supported |

None of these can be used in an API Product.

## Dynamic Client Registration (DCR) for OAuth 2.0

<Note>
This is OAuth 2.0 with an external Identity Provider (IdP), a different mechanism from [Tyk OAuth 2.0](/api-management/authentication/oauth-2) (unsupported, see [above](#unsupported-authentication-types)). Here, the IdP issues the token and Tyk only validates it.
</Note>

APIs secured with JSON Web Tokens (JWT) get those tokens from an external IdP, not from Tyk. So when an API Consumer requests access, the Portal can't just hand them a token the way it does for an Auth Token.

Instead, it registers a new OAuth 2.0 client with the IdP on the Consumer's behalf, using [Dynamic Client Registration (DCR)](/tyk-stack/tyk-developer-portal/enterprise-developer-portal/api-access/dynamic-client-registration). The IdP returns a `client_id` and `client_secret`, which the Consumer uses to get a JWT and present to Tyk Gateway. Tyk validates the JWT and creates a [Session](/api-management/access-control/overview#2-dynamically-generated-sessions) on the fly, so there's no need to pre-register the client with Tyk itself.

This is different from the [Authentication Token](/api-management/authentication/bearer-token) method, where Tyk issues the credential directly.

### Supported Identity Providers

| Identity Provider | Support | Notes |
|---|---|---|
| Keycloak | Fully supported | N/A |
| Okta | Fully supported | Requires the `OktaAppType` field (`web`, `native`, `browser`, or `service`). For Client Credentials flow, set the allowed response type to `token` only. |
| Gluu | Fully supported | N/A |
| Curity | Supported via Other type | Curity requires authentication on its DCR endpoint by default. Workaround: disable DCR endpoint authentication in Curity (no-authentication mode). |
| Any RFC-compliant IdP | Supported via Other type | Select **Other** in the DCR template settings. Full compatibility isn't guaranteed. |
