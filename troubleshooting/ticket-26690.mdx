## Overview

In Tyk Enterprise Developer Portal deployments, monitoring systems may capture frequent error-level logs containing *renderpage.Find : "record not found"* accompanied by stack traces originating from *helpers.go*. These messages commonly reference paths such as */hello* or automated scanner targets such as */.env*, */config.js*, */composer.json*, and */Dockerfile*.

## Root Cause

The Enterprise Developer Portal routes requests that do not match internal APIs or static assets to a CMS wildcard catch-all handler. When an unauthenticated request arrives for an unmapped path, the portal queries the database to locate a published CMS page. If no matching record is found, GORM returns a record not found error. The portal logs this lookup failure at **error** level before rendering the standard 404 response. In default production logging mode, error-level entries automatically attach a stack trace.

Frequent misses for */hello* typically indicate that container health checks or uptime monitors were configured using Tyk Gateway or Tyk Dashboard templates. Tyk Gateway and Dashboard expose */hello* for health checks, whereas the Enterprise Developer Portal exposes */live* and */ready*.

Requests for configuration or environment paths typically originate from automated internet vulnerability scanners probing public endpoints.

## Remediation and Best Practices

To eliminate unnecessary error logs and distinguish expected traffic from operational faults, apply the following steps:

1. **Update Health Probes:** Configure Kubernetes liveness and readiness probes or load balancer health monitors to use */live* and */ready* instead of */hello*.

   ```
   livenessProbe:
     httpGet:
       path: /live
       port: 3001
     initialDelaySeconds: 15
     periodSeconds: 10
   readinessProbe:
     httpGet:
       path: /ready
       port: 3001
     initialDelaySeconds: 20  periodSeconds: 10
   ```
2. **Filter Scanner Noise at Ingress:** Block or filter automated vulnerability scanner paths at the ingress controller, API gateway, or Web Application Firewall layer before requests reach the portal service.
3. **Review Logging Configuration:** Manage portal logging output using the *PORTAL_LOG_LEVEL* environment variable. Note that setting the log level to error will still output page lookup misses as designed by the CMS router.

## Verification

Verify that dedicated portal probe endpoints return successful responses:

```
curl -I 
curl -I 
```

Inspect centralized monitoring to confirm that *renderpage.Find /hello* error log entries cease once the probe target has been updated.

## Applies To

- Tyk Enterprise Developer Portal
- Kubernetes and Helm deployments
- Self-managed deployments
