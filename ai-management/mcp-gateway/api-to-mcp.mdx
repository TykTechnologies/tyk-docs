Tyk Gateway can generate an MCP proxy directly from a Tyk-managed REST API's OpenAPI specification, turning its operations into MCP tools without you building, hosting, or maintaining a separate MCP server. This page explains how this works, how it differs from fronting a remote MCP server, and what it does and doesn't support in this release.

## What it is

Every MCP proxy in Tyk Gateway does one of two things: it fronts a **remote MCP server** you've built and are hosting elsewhere, or it's **generated directly from a Tyk-managed REST API**, with no separate server involved at all. This page covers the second case.

To generate a proxy this way, you reference an existing [Tyk OAS API](/ai-management/mcp-gateway/mcp-proxy-definitions), and Tyk derives an MCP tool for each REST operation you choose to expose. Calling that tool sends a JSON-RPC `tools/call` request to the MCP proxy, which Tyk translates into an ordinary REST request against the paired API and wraps the response back into the MCP result format the calling agent expects. No changes to the source REST API are required: you don't touch its OpenAPI spec, its code, or its existing consumers to expose it to agents.

OpenAPI specs are usually written for human developers or system-to-system integration, not for an agent deciding which tool to call — a cryptic `operationId` or an undocumented parameter can leave a perfectly functional operation hard for an agent to use well. You can override a tool's name and description, and each parameter's name and description, directly at the proxy layer, making an existing API agent-ready without editing its OpenAPI spec. See [How the tool catalogue works](#how-the-tool-catalogue-works) below.

You're also not limited to one proxy per API. A single REST API can be the source for multiple MCP proxies, each with its own tool selection, enrichment, and policies — useful for carving a large API into purpose-built tool catalogues, such as a read-only proxy for a reporting agent and a separate write-enabled proxy for an operations agent. See [How to slice one API into multiple MCP proxies](/ai-management/mcp-gateway/how-to-slice-one-api-into-multiple-mcp-proxies).

The MCP proxy is itself a distinct consumer of the source REST API, authenticating with its own credential and governed by its own security policy — entirely independent of the keys and policies your existing REST consumers use. This matters because agents call APIs differently to how humans and services do: an agent decides autonomously which operations to invoke, can be manipulated into calling tools it shouldn't through prompt injection, and generates far less predictable traffic patterns. You can govern that traffic with its own tool allowlists, rate limits, and RBAC, without touching your source API.

## How the tool catalogue works

Tyk builds the tool catalogue by reading the source API's OpenAPI operations. Each operation's `operationId` becomes the tool name; operations without one get a deterministic name derived from their HTTP method and path instead. See [Tool naming and discovery](/ai-management/mcp-gateway/core-concepts#tool-naming-and-discovery) for exactly how names are derived and how collisions are resolved.

All operations become tools by default. To narrow that down, create an explicit allow list in the `x-tyk-mcp-server` extension — listing only the operations you want exposed as `allow: true` entries — through whichever interface you use to manage the proxy (see [Creating and managing a proxy](#creating-and-managing-a-proxy) below). You can also override a tool's name and description, and each parameter's name and description, independently of the source API's own OpenAPI document — useful when the source spec's own naming isn't clear enough for an agent to use reliably.

Because the catalogue is derived from the source API's OpenAPI specification at gateway load time, rather than stored as a fixed, independent snapshot, changes to the source API's operations are picked up on the next gateway reload. Without an allow list, newly added operations become tools automatically; with one, you need to add new operations to it yourself, since only what's explicitly allowed is exposed.

This tool catalogue configuration lives in an `x-tyk-mcp-server` vendor extension on the MCP proxy's own OAS definition, alongside the `x-tyk-api-gateway` extension every MCP proxy has. See [REST API to MCP x-tyk-mcp-server extension](/ai-management/mcp-gateway/api-to-mcp-definitions) for the full schema.

## Creating and managing a proxy

An MCP proxy generated this way is still just a [Tyk OAS API definition](/ai-management/mcp-gateway/mcp-proxy-definitions) with the `x-tyk-mcp-server` extension added, so any interface that manages a Tyk OAS API definition can create and manage one:

- **Tyk Dashboard** — a guided wizard walks you through selecting the source API, choosing which operations to expose, and overriding tool and parameter names and descriptions, with a preview before you save. See [Managing MCP proxies](/ai-management/mcp-gateway/managing-proxies).
- **Tyk Operator** — declare the OAS document, including the `x-tyk-mcp-server` extension, in a `ConfigMap` referenced by a `TykMcpProxyDefinition` custom resource, managed the same way as any other Tyk API in a GitOps workflow. See [Tyk Operator: MCP proxies](/product-stack/tyk-operator/mcp-proxy#managing-a-proxy-generated-from-a-tyk-managed-rest-api).
- **Tyk Gateway API and Dashboard API** — create, update, and delete the OAS definition directly, including a dry-run mode that previews the expanded tool catalogue without persisting it. See [MCP Gateway API extensions](/ai-management/mcp-gateway/mcp-api-extensions).

Which interface you use doesn't change how the proxy behaves at runtime: the tool catalogue, enrichment overrides, and everything else on this page apply identically regardless of how the definition was authored.

## Requirements and v1 limitations

Generating an MCP proxy from a REST API requires **Tyk Enterprise Edition** for the proxy type itself, not just for individual features within it. See [Requirements](/ai-management/mcp-gateway/overview#requirements) for the full licensing comparison against pass-through MCP proxies.

The following limitations apply in this release:

| Limitation | Detail |
|---|---|
| Source API format | The source must be a Tyk OAS API already onboarded to Tyk. GraphQL APIs and Tyk Classic API definitions aren't supported as a source. |
| One proxy, one source | An MCP proxy pairs with exactly one source REST API. You can't combine operations from multiple REST APIs behind a single proxy. The reverse, slicing one REST API's operations across several MCP proxies, is supported: see [How to slice one API into multiple MCP proxies](/ai-management/mcp-gateway/how-to-slice-one-api-into-multiple-mcp-proxies). |
| Request body types | Source operations whose request bodies use multipart, XML, or binary content types can't be exposed as MCP tools. |
| Response size | Upstream responses are capped at 1 MiB and truncated beyond that. The cap isn't configurable. |
| Transport | Only `POST /mcp` is supported. `GET /mcp`, SSE streaming, and server-initiated notifications aren't available. |
| Primitives | A proxy generated this way only ever produces tools. Resources and prompts aren't applicable, since a REST operation has no equivalent primitive. |
| Behavioural hints | `readOnlyHint`, `destructiveHint`, `idempotentHint`, and `openWorldHint` can be set directly in the `x-tyk-mcp-server` extension — for example via Tyk Operator or the API — but the Tyk Dashboard's wizard and designer don't yet expose a UI control for them. |

## Summary

Generating an MCP proxy directly from a Tyk-managed REST API turns that API's operations into MCP tools without a separate MCP server to build or run. The proxy authenticates against the source API as its own consumer, and its tool catalogue is derived from the source OpenAPI specification and kept in sync on every gateway reload.

See [Creating and managing a proxy](#creating-and-managing-a-proxy) for the available interfaces, [MCP proxy definitions](/ai-management/mcp-gateway/mcp-proxy-definitions) for the underlying schema, and [MCP Gateway: Core Concepts](/ai-management/mcp-gateway/core-concepts) for how tool naming, discovery, and primitives work across both proxy types.
