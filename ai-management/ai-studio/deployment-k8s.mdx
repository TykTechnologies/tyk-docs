## Availability

| Edition   | Deployment Type |
| :------------- | :---------------------- |
| [Enterprise](/ai-management/ai-studio/overview#enterprise-edition) | Self-Managed |

<Note>
This guide focuses on the Enterprise Edition of Tyk AI Studio. For the Community Edition, please refer to the [Tyk AI Studio GitHub repository](https://github.com/TykTechnologies/ai-studio/blob/main/docs/site/docs/deployment-helm-k8s.md). The Community Edition uses different Docker images (`tykio/tyk-ai-studio` and `tykio/tyk-microgateway`) and does not require a license key.
</Note>

This guide explains how to deploy Tyk AI Studio (control plane), an Edge Gateway (data plane), and PostgreSQL on Kubernetes using Helm. AI Studio manages configuration centrally and the Edge Gateway processes AI requests, receiving configuration via gRPC.

<Note>
The Helm chart uses the older name `microgateway` for the Edge Gateway component. Examples are the `microgateway:` values block and the `tykio/tyk-microgateway-ent` image. This guide uses "Edge Gateway" in prose for the same component.
</Note>

## Prerequisites

- Kubernetes 1.16+
- Helm 3.0+
- `kubectl` configured with access to your cluster
- A Tyk AI License key (contact support@tyk.io or your account manager to obtain)
- For production with TLS: cert-manager installed in your cluster

<Note>
Running on Podman, containerd, or another container runtime? See [Container Runtimes](/deployment-and-operations/container-runtimes).
</Note>

## Generate Secrets

The Helm chart leaves these secrets empty. Set them with the keys that you generate here. See [Tyk AI Studio](/deployment/default-secrets-reference#tyk-ai-studio) in the Default Secrets Configuration Reference.

Before installing, generate three secret keys to secure communication and encrypt data:

```bash expandable
# Secret key for encryption (used for secrets management and SSO)
openssl rand -hex 16
# Example output (sample only, generate your own): xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

# Encryption key for Edge Gateway communication (must be exactly 32 hex chars)
openssl rand -hex 16
# Example output (sample only, generate your own): yyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyy

# gRPC auth token (for hub-spoke communication)
openssl rand -hex 16
# Example output (sample only, generate your own): zzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzz
```

Save these values — you will substitute them into the values file below.

## Option 1: Testing / Quickstart

For local development or test clusters. Uses NodePort services, internal PostgreSQL, and no ingress.

### 1. Add the Helm Chart

The Helm chart is in the [Tyk AI Studio GitHub repository](https://github.com/TykTechnologies/ai-studio).

```bash
git clone https://github.com/TykTechnologies/ai-studio.git
cd ai-studio/helm
helm dependency update .
```

### 2. Create `values-testing.yaml`

Replace the placeholder secrets with your generated values. The `grpcAuthToken` / `edgeAuthToken` and `microgatewayEncryptionKey` / `encryptionKey` pairs **must match**.

```yaml Expandable expandable
midsommar:
  image:
    repository: tykio/tyk-ai-studio-ent
    tag: v2.3.0
  service:
    type: NodePort
    ports:
      - name: http
        port: 8080
        targetPort: 8080
        nodePort: 32580
      - name: gateway
        port: 9090
        targetPort: 9090
        nodePort: 32590
      - name: grpc
        port: 50051
        targetPort: 50051

config:
  allowRegistrations: "true"
  siteUrl: "http://localhost:32580"                       # Update post-install if not localhost
  fromEmail: "noreply@localhost"
  devMode: "true"                                       # Required for login over plain HTTP
  databaseType: "postgres"
  tykAiSecretKey: "CHANGE-ME-first-secret"
  tykAiLicense: "your-license-key"
  ociCacheDir: "./data/cache/plugins"
  ociRequireSignature: "false"                          # Development only: loads unsigned plugins (default "true")
  gatewayMode: "control"
  grpcPort: "50051"
  grpcHost: "0.0.0.0"
  grpcTlsInsecure: "true"
  grpcAuthToken: "CHANGE-ME-third-secret"
  microgatewayEncryptionKey: "CHANGE-ME-second-secret"
  # proxyUrl auto-resolves to the Edge Gateway k8s service — no need to set it

database:
  internal: true
  user: "tyk"
  password: "your-db-password"
  name: "tyk_ai_studio"

postgres:
  persistence:
    enabled: true
    size: 1Gi

microgateway:
  enabled: true
  image:
    repository: tykio/tyk-microgateway-ent
    tag: v2.3.0
  service:
    type: NodePort
    port: 8080
    nodePort: 32591
  config:
    edgeNamespace: "default"
  secrets:
    edgeAuthToken: "CHANGE-ME-third-secret"             # Must match config.grpcAuthToken
    encryptionKey: "CHANGE-ME-second-secret"             # Must match config.microgatewayEncryptionKey
    tykAiLicense: "your-license-key"
```

### 3. Install

```bash
helm install midsommar . -f values-testing.yaml
```

### 4. Set External Gateway URL

The Edge Gateway's internal service URL is used for routing by default, but the AI Portal needs to display the correct external URL for tools and datasources. After install, patch the config with your cluster's node IP:

```bash
# Get the node IP and set the gateway URL
NODE_IP=$(kubectl get nodes -o jsonpath='{.items[0].status.addresses[?(@.type=="InternalIP")].address}')
GATEWAY_URL="http://${NODE_IP}:32591"

# Patch the configmap with correct URLs and restart AI Studio
STUDIO_URL="http://${NODE_IP}:32580"
kubectl patch configmap midsommar-config -p \
  "{\"data\":{\"SITE_URL\":\"${STUDIO_URL}\",\"TOOL_DISPLAY_URL\":\"${GATEWAY_URL}\",\"DATASOURCE_DISPLAY_URL\":\"${GATEWAY_URL}\"}}"
kubectl rollout restart deployment midsommar
```

<Note>
**Tip:** If you know your cluster's external IP or hostname upfront, you can skip this step by setting `config.toolDisplayUrl` and `config.datasourceDisplayUrl` in your values file instead.
</Note>

### 5. Verify

```bash
# Check all pods are running
kubectl get pods

# Check AI Studio health (via NodePort)
curl -s http://${NODE_IP}:32580/health

# Check Edge Gateway health (via NodePort)
curl -s http://${NODE_IP}:32591/health
```

<Note>
If you cannot reach the node IP from your machine (for example, with kind or Docker Desktop on macOS), use `kubectl port-forward` instead:

```bash
kubectl port-forward svc/midsommar 8080:8080
```

Then open `http://localhost:8080`. In step 4, set `SITE_URL` to `http://localhost:8080`.
</Note>

| Port | URL | Purpose |
|------|-----|---------|

| 32590 | `http://<node-ip>:32590` | Embedded AI Gateway |

## Option 2: Production with TLS

For production deployments with Ingress, TLS via cert-manager, and an external database.

### 1. Create `values-production.yaml`

Replace all placeholder values with your actual configuration.

```yaml Expandable expandable
midsommar:
  image:
    repository: tykio/tyk-ai-studio-ent
    tag: v2.3.0
  ingress:
    enabled: true
    certificateEnabled: true
    className: nginx
    certManager:
      issuer: letsencrypt-prod
    hosts:
      - host: studio.yourdomain.com
        paths:
          - path: /
            pathType: Prefix
            port: 8080
    tls:
      - secretName: studio-tls-secret
        hosts:
          - studio.yourdomain.com
  service:
    ports:
      - name: http
        port: 8080
        targetPort: 8080
      - name: gateway
        port: 9090
        targetPort: 9090
      - name: grpc
        port: 50051
        targetPort: 50051

config:
  allowRegistrations: "true"
  siteUrl: "https://studio.yourdomain.com"
  fromEmail: "noreply@yourdomain.com"
  devMode: "false"
  databaseType: "postgres"
  tykAiSecretKey: "CHANGE-ME-first-secret"
  tykAiLicense: "your-license-key"
  ociCacheDir: "./data/cache/plugins"
  ociRequireSignature: "true"
  gatewayMode: "control"
  grpcPort: "50051"
  grpcHost: "0.0.0.0"
  grpcTlsInsecure: "true"                               # Set to "false" with TLS certs
  grpcAuthToken: "CHANGE-ME-third-secret"
  microgatewayEncryptionKey: "CHANGE-ME-second-secret"
  # proxyUrl, toolDisplayUrl, datasourceDisplayUrl auto-resolve from Edge Gateway ingress config

database:
  internal: false
  url: "postgres://user:password@your-db-host:5432/tyk_ai_studio?sslmode=require"

microgateway:
  enabled: true
  image:
    repository: tykio/tyk-microgateway-ent
    tag: v2.3.0
  ingress:
    enabled: true
    certificateEnabled: true
    className: nginx
    certManager:
      issuer: letsencrypt-prod
    hosts:
      - host: gateway.yourdomain.com
        paths:
          - path: /
            pathType: Prefix
    tls:
      - secretName: gateway-tls-secret
        hosts:
          - gateway.yourdomain.com
  config:
    edgeNamespace: "default"
    allowInsecure: "false"
    tlsEnabled: "false"                                  # gRPC client TLS to AI Studio
  secrets:
    edgeAuthToken: "CHANGE-ME-third-secret"
    encryptionKey: "CHANGE-ME-second-secret"
    tykAiLicense: "your-license-key"
```

### 2. Install

Run these commands from the `ai-studio/helm` directory. To get the chart, follow [step 1 of Option 1](#1-add-the-helm-chart).

```bash
helm dependency update .
helm install midsommar . -f values-production.yaml
```

### 3. Verify

```bash
kubectl get pods
kubectl get ingress
curl -s https://studio.yourdomain.com/health
curl -s https://gateway.yourdomain.com/health
```

## After Deployment

### First User Registration

After you start the services, create the first user:

1. Open your configured `siteUrl` (for example, `https://studio.yourdomain.com`) in your browser.
2. Select **Sign up**, then enter a name, an email address, and a password.
3. Log in with the new account.

<Note>
The first user who registers becomes the administrator. You can use any email address. Other users must verify their email address before they can log in, so configure SMTP before you invite them. AI Studio ignores the deprecated `ADMIN_EMAIL` variable.
</Note>

### Add Your API Keys

AI Studio pre-populates OpenAI and Anthropic LLM configurations on first startup with placeholder secrets (`OPENAI_KEY` and `ANTHROPIC_KEY`). To start using them:

1. Open AI Studio at the `siteUrl` you configured and log in with your admin account
2. Navigate to **Settings → Secrets** in the sidebar
3. Click on **`OPENAI_KEY`** and edit it to add your OpenAI API key
4. Click on **`ANTHROPIC_KEY`** and edit it to add your Anthropic API key

### Push Configuration to the Edge Gateway

1. Navigate to **Portal administration → Edge Gateways** in the sidebar
2. Verify that your Edge Gateway shows as **Connected**. Its Edge ID is the pod name, for example `midsommar-microgateway-64b5f9879d-mf5p2`.
3. Click **Push Configuration** to sync the latest settings to the Edge Gateway

Once the sync status shows **Synced**, the Edge Gateway is ready to proxy LLM requests.

For further setup (additional LLMs, users, applications), see the **[Initial Configuration](/ai-management/ai-studio/configuration)** guide.

## Advanced Configuration

### Several AI Studio Replicas

From v2.3, several AI Studio replicas can serve one PostgreSQL database. Set `replicaCount` above `1`. The chart then needs:

- An external PostgreSQL database (`database.internal: false`). The bundled PostgreSQL is a single pod, and SQLite serves one process, so the render fails with either.
- One `CSRF_KEY` for every replica (`config.csrfKey`). Generate it with `openssl rand -hex 32`. The render fails without it.

With `replicaCount` above `1`, the chart also renders:

- A rolling update that starts a new replica before it stops an old one. With one replica, the strategy stays `Recreate`.
- A PodDisruptionBudget that keeps `podDisruptionBudget.minAvailable` (`1`) replicas through node drains.
- A spread of the replicas over nodes and zones.
- Cookie affinity on the nginx Ingress (`midsommar.ingress.sessionAffinity`). Chat, agent, and MCP SSE sessions stay on the replica that started them. For another ingress controller, set its own affinity annotations.

The readiness probe uses `/ready`. Set `probes.readiness.requireWrite: true` to probe `/ready?require=write` instead.

At startup, AI Studio waits for its database for up to `DATABASE_STARTUP_TIMEOUT` (60 seconds by default){/* TODO: link reference for DATABASE_STARTUP_TIMEOUT */}. Then it runs its migrations. During this time, neither `/health` nor `/ready` answers. The chart has a startup probe on `/health` that allows `probes.startup.periodSeconds` × `probes.startup.failureThreshold`, 180 seconds by default. Keep it longer than the database wait plus the migration time. Increase it for the first start of a new version on a large database.

When a replica stops, the chart keeps the pod serving for `shutdown.preStopDelaySeconds` (10 seconds) while Kubernetes removes it from the Service. AI Studio then lets the requests in flight finish for up to 30 seconds. The default grace period is 45 seconds. The delay uses the `sleep` preStop action of Kubernetes 1.30 and later. On an older cluster, the chart renders no preStop hook, and a rolling update can refuse a few requests.

To keep the database credentials out of your values file, put the full `DATABASE_URL` in a Secret and set `database.existingSecret` (key `DATABASE_URL`, or `database.existingSecretKey`).

```yaml
replicaCount: 3

database:
  internal: false
  existingSecret: studio-database   # key DATABASE_URL

config:
  csrfKey: "<openssl rand -hex 32>"
  databaseConnectTimeout: "3s"

# The in-memory chat queue works only on one replica
extraEnv:
  - name: QUEUE_TYPE
    value: "postgres"
```

The upgrade to v2.3 is not rolling. Stop every older replica before the first v2.3 replica starts. For this upgrade, set `midsommar.strategy.type: Recreate`, or scale to one replica first.

To run AI Studio in two clusters over one replicated PostgreSQL database, refer to [Active-Active Deployment of Tyk AI Studio](/ai-management/ai-studio/deployment-active-active).

### Message Queue (NATS)

For distributed deployments with message persistence, set the NATS variables with `extraEnv` in your values file. The chart has no dedicated values for the queue. For all NATS variables, refer to [NATS JetStream Configuration](/ai-management/ai-studio/installation/nats).

```yaml
extraEnv:
  - name: QUEUE_TYPE
    value: "nats"
  - name: NATS_URL
    value: "nats://nats-server:4222"
  - name: NATS_STORAGE_TYPE
    value: "file"
  - name: NATS_RETENTION_POLICY
    value: "interest"
  - name: NATS_MAX_AGE
    value: "4h"
  - name: NATS_TLS_ENABLED
    value: "true"
  - name: NATS_CREDENTIALS_FILE
    value: "/etc/nats/user.creds"
```

### Scaling Edge Gateways

Each Edge Gateway pod registers with AI Studio under its own pod name as its Edge ID.

#### Use the StatefulSet Form

A Deployment keeps the Edge Gateway database on an `emptyDir` volume. The volume survives a container restart, but a rescheduled pod starts with an empty database. Set `microgateway.kind: StatefulSet` and `microgateway.persistence.enabled: true` when the Edge Gateway must keep its database across a rescheduling:

- With `config.startFromLastKnownGood`, the Edge Gateway starts from the configuration stored in its database.
- With `config.credentialSync: full` (Enterprise), the Edge Gateway validates keys from the list stored in its database.
- A StatefulSet pod keeps its name, for example `midsommar-microgateway-0`, so the edge keeps its entry in AI Studio.

The chart shows a warning after install when you set `startFromLastKnownGood` or `credentialSync: full` without StatefulSet persistence.

#### Several Control Planes

From v2.3.0, the Edge Gateway chart has values for several control planes and for control-plane outages:

```yaml expandable
microgateway:
  kind: StatefulSet
  persistence:
    enabled: true
  config:
    controlEndpoints:
      - studio.region-a.example.com:50051
      - studio.region-b.example.com:50051
    controlFailbackInterval: "5m"     # Optional: go back to the first endpoint
    startFromLastKnownGood: true      # Optional: start from the stored configuration
    # startupControlTimeout: "30s"
    # lastKnownGoodMaxAge: "72h"
    # credentialSync: "full"          # Enterprise: validate keys from a synced, hashed list
    # credentialSyncMaxAge: "24h"
```

`controlEndpoints` replaces `controlEndpoint` when it is not empty. Keep `probes.startup` (`periodSeconds` × `failureThreshold`, 150 seconds by default) longer than `startupControlTimeout`. For the behavior of each setting, refer to [Edge Gateway Resilience](/ai-management/ai-studio/manage-edge-gateway#edge-gateway-resilience).

#### Size the Volume

The Edge Gateway stores one analytics row for each request, for `config.analyticsRetentionDays` (90 days in the chart). Each request uses about 400 bytes. The default `persistence.size` of 2Gi with 90 days holds less than one request per second. AI Studio also receives these records through the analytics pulse, so a short retention, such as `"1"`, is often enough on the edge:

| Requests per Second | 1 Day | 7 Days | 90 Days |
| :--- | :--- | :--- | :--- |
| 1 | 35 MB | 240 MB | 3 GB |
| 10 | 350 MB | 2.4 GB | 31 GB |
| 100 | 3.5 GB | 24 GB | 310 GB |

When the volume is full, the Edge Gateway continues to serve, but it cannot apply a configuration push. Its `/ready` response shows `"database_full": true`.

#### Size the Memory

From v2.3.0, the chart requests 256Mi of memory and sets a 1Gi limit for each Edge Gateway. Set the request to what your edges use under load. During a control-plane outage, the Edge Gateway keeps undelivered analytics in memory, up to `analyticsPulse.maxBacklogBytes` (64 MiB). The working set of the edge, plus the backlog, plus about 50 MB must stay below 85% of the memory limit. Above 85%, the Edge Gateway refuses new requests (`OVERLOAD_MEMORY_THRESHOLD`). Increase the limit and the backlog together.

#### Separate Edge Gateways for Each Region

To deploy Edge Gateways for different regions, deploy a separate Helm release for each region and set a different `edgeNamespace`:

```yaml
microgateway:
  config:
    edgeNamespace: "eu-west"
```

Each Edge Gateway receives only the configuration assigned to its namespace.

<Note>
A Deployment gives each pod a new name after a restart, and AI Studio removes the stale entries. For stable Edge IDs (for example, `midsommar-microgateway-0`), set `microgateway.kind: StatefulSet`.
</Note>

## Maintenance

### Upgrading

```bash
helm upgrade midsommar . -f your-values.yaml
```

With one replica, the AI Studio Deployment uses the `Recreate` strategy (`midsommar.strategy`). Kubernetes stops the old AI Studio pod before it starts the new one, so two AI Studio instances never run at the same time. During an upgrade, AI Studio is not available for a short time. Edge Gateways continue to serve traffic. With `replicaCount` above `1`, the chart uses a rolling update by default.

Before you upgrade to v2.3.0:

1. Get a v2.3 license (Enterprise). AI Studio and Enterprise Edge Gateways on v2.3.0 do not start with an older license.
2. Take a database backup. To roll back, you must restore the backup.
3. With `replicaCount` above `1`, set `midsommar.strategy.type: Recreate` for this upgrade, or scale to one replica. An older replica on a v2.3 database refuses every App key.
4. Upgrade the Edge Gateways together with AI Studio. Refer to [Upgrade Edge Gateways With AI Studio](/ai-management/ai-studio/manage-edge-gateway#upgrade-edge-gateways-with-ai-studio).

{/* TODO: link to the AI Studio 2.3.0 upgrade notes once merged */}

From v2.3.0, the Edge Gateway chart has new memory defaults. If your values do not set `resources`, the Edge Gateway pods get them and are recreated at the upgrade. Refer to [Size the Memory](#size-the-memory).

If your values set `nameOverride` or `fullnameOverride` and no Edge Gateway control endpoint, `helm upgrade` fails with a message that names the endpoint to set. Set `microgateway.config.controlEndpoint` to that value, or set `microgateway.enabled: false` if you do not use the bundled Edge Gateway.

### Uninstalling

```bash
helm uninstall midsommar
```

### Viewing Logs

```bash
# AI Studio logs
kubectl logs -l app.kubernetes.io/name=midsommar

# Edge Gateway logs
kubectl logs -l app=microgateway

# Database logs (internal postgres)
kubectl logs -l app=postgres
```

For more detail, increase the log level. From v2.3.0, `config.logLevel` sets [`LOG_LEVEL`](/ai-management/ai-studio/ai-studio-env#log_level) for AI Studio. The Edge Gateway chart has its own `microgateway.config.logLevel`:

```bash
helm upgrade midsommar . --reuse-values --set config.logLevel=debug
```

## Troubleshooting

<AccordionGroup>

<Accordion title="Check pod and ingress status">

```bash
kubectl get pods
kubectl get ingress
kubectl describe pod <pod-name>
````

</Accordion>

<Accordion title="Common Issues">

* **Database connection failures**: Check credentials and network access
* **Ingress not working**: Verify DNS records and TLS configuration
* **Login fails on HTTP**: Set `devMode: "true"` — session cookies require this when not using HTTPS
* **Marketplace page is empty**: Set `ociCacheDir: "./data/cache/plugins"` in your config values — the marketplace service will not start without it
* **Plugin refused because its signature does not verify**: From v2.3.0, AI Studio and the Edge Gateway verify signatures themselves (Enterprise), and require them by default (`config.ociRequireSignature` and `microgateway.config.ociPluginsRequireSignature`). Configure the signing key of the plugin, or set these values to `"false"` to load unsigned plugins. Refer to [Signature Verification](/ai-management/ai-studio/plugins/security#signature-verification)

</Accordion>

<Accordion title="Pods restart during the first install">

On the first install, the AI Studio pod can restart until PostgreSQL is ready. The Edge Gateway pod can restart until the AI Studio gRPC server is ready. These restarts are normal. The pods recover without action. Check that all pods show `Running` and `READY 1/1`:

```bash
kubectl get pods
```

</Accordion>

<Accordion title="Registration fails with an unexpected error">

In AI Studio v2.1.x, over plain HTTP, the CSRF check accepts browser requests only from `localhost:3000`. Registration from any other address fails with `403 Forbidden - origin invalid`. Upgrade to v2.2.0 or later. From v2.2.0, AI Studio also accepts requests from the host in `SITE_URL`.

</Accordion>

<Accordion title="Edge Gateway cannot connect to AI Studio">

* Verify the Edge Gateway pod logs:

```bash
kubectl logs -l app=microgateway
```

* Check that `CONTROL_ENDPOINT` resolves to the AI Studio service. By default, the bundled Edge Gateway uses the AI Studio Service of the release. For a release named `midsommar`, this is `midsommar:50051`.
* Verify `edgeAuthToken` matches `grpcAuthToken` exactly
* Verify `encryptionKey` matches `microgatewayEncryptionKey` exactly
* Check that `GATEWAY_MODE=control` is set in AI Studio config

</Accordion>

</AccordionGroup>
