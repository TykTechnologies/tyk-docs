<Note>
Filters are an Enterprise Edition feature. In the Community Edition, the API refuses to create, update, or test a filter, with the error `Enterprise Feature`. AI Studio does not run an existing filter. Each filter passes the content through without changes, and AI Studio logs a warning.

## Filter Types

A filter is one of two types. You select the type in **Filter type** on the filter form.

| Type | What it does |
| :--- | :--- |
| **Script** | Runs Tengo code that you write against the request or the response. To write one, refer to [Create a Script Filter](/ai-management/ai-studio/how-to-create-script-filter). |
| **Guardrail** (Enterprise Edition) | Runs a detection [provider](/ai-management/ai-studio/guardrails#providers) and blocks, redacts, quarantines, or logs the content when the provider finds a match. You do not write code. From 2.3.0, it also examines tool results, tool calls, and tool definitions. |

Both types attach, run, and record compliance events in the same way. In the API, the type is the `kind` field of a filter (`script` or `guardrail`). New Enterprise installations include five [default guardrails](/ai-management/ai-studio/guardrails#default-guardrails).

For guardrail providers, detectors, and actions, refer to [Guardrails](/ai-management/ai-studio/guardrails).

## Blocking and Modification

Filters process the prompts and data that go to LLMs through the AI Gateway or Chat Rooms. A filter can block content, change it, or both:

1. **Blocking**: Analyze message content, metadata, and context, and deny requests that violate policies. For example, block prompts that contain PII, sensitive keywords, or unauthorized patterns.
2. **Modification**: Transform message content before it reaches the LLM or after tool responses. For example, redact emails, phone numbers, and SSNs, or add safety instructions to system prompts.
3. **Combined**: Inspect and modify in a single script. For example, redact emails from user messages, but block if an SSN is detected.

Filters run at these points:

- **Request Filters**: Modify/block requests before reaching LLM
  - LLM Proxy Requests (before reaching LLM)
  - Chat Session Messages (before RAG search and LLM)
  - File Content (before RAG indexing)
  - Tool Responses (after tool execution)
- **Response Filters**: Block LLM responses based on content
  - LLM Proxy Responses (REST and streaming)
  - Chat Session Responses (regular and streaming)
- **Tool Filters**: Run on the arguments sent to a tool and on the response from the tool. Refer to [Tool Filters](#tool-filters).

When you attach several filters to an LLM, they run from top to bottom in the order on the LLM form. Use the arrows on the form to change the order. The first filter that blocks stops the request. AI Studio stores the order and sends it to Edge Gateways.

For the script input and output objects, helper functions, and runtime limits, refer to [Filter Scripting Reference](/ai-management/ai-studio/filter-scripting-reference).

## Response Filters

Response filters block LLM responses based on content analysis. They control what LLMs can say to end users. To write one, refer to [Filter LLM Responses](/ai-management/ai-studio/how-to-filter-responses).

1. **Block-Only**: Response filters can only block responses, not modify them
2. **Works on LLM Responses**: On LLMs and chat, response filters run on the LLM response. On tools, the same flag selects the tool output direction. Refer to [Tool Filters](#tool-filters).
3. **Streaming Support**: Execute per-chunk during streaming with access to accumulated buffer
4. **Script-Controlled**: Filter scripts decide when to evaluate based on buffer length
5. **Fail Open**: On LLM responses, a script error or timeout lets the response through

Use request filters to keep sensitive data away from the LLM. For example, redact PII before the LLM gets it, or enforce input policies.

Use response filters to control what the LLM says. For example, stop commitments such as refunds or promises, block harmful output, or enforce corporate communication policies.

### Response Filter Execution

**Proxy (REST)**:
- Executes after response hooks (if any)
- Full response available in `input.raw_input`
- If blocked: Error returned to client instead of response

**Proxy (Streaming)**:
- Executes on every chunk
- Executes one more time when the stream is complete, with `is_final: true`, an empty `raw_input`, and the full response in `current_buffer`. A short response that never reached the buffer threshold of the script is then still checked.
- Access to both `raw_input` (current chunk) and `current_buffer` (accumulated text)
- If blocked: Streaming stops, error sent to client
- If blocked on the final run: The stream ends with an error event, and AI Studio logs a blocked response. The chunks that the client already received are not removed. To block content before the client receives it, check `current_buffer` on each chunk. Do not rely only on the final run.

**Chat (Non-Streaming)**:
- Executes before adding to chat history
- If blocked: Error published to queue instead of response

**Chat (Streaming)**:
- Executes on every chunk before publishing to queue
- If blocked: Error published, streaming callback returns error to stop further chunks

## Tool Filters

You can attach filters to [tools](/ai-management/ai-studio/tools). Tool filters run in two directions:

| Filter direction | When it runs | What the script gets |
| :--- | :--- | :--- |
| Request filter (**Is this a Response Filter?** cleared) | Before AI Studio calls the tool | The tool call arguments, as JSON |
| Response filter (**Is this a Response Filter?** selected) | After the tool returns, before the response goes to the caller | The tool response body |

Tool filters run on every way that a tool is called: in chat, on the REST endpoint, and on all MCP transports. They run on AI Studio and on Edge Gateways. To write one, refer to [Filter Tool Calls](/ai-management/ai-studio/how-to-filter-tool-calls).

Tool filters fail closed in both directions. If a filter blocks the call, or the script fails, the caller gets a generic refusal: HTTP `403` with `blocked by policy`, or the MCP equivalent.

The refusal is the same for input and output blocks. It does not contain the filter name or the reason, so a caller cannot use it to learn your filter configuration. AI Studio writes the reason to the logs and records a [compliance event](/ai-management/ai-studio/compliance-events) for every block.

## Filter Execution Order in Chat Sessions

When a user sends a message in a chat session, filters are executed at multiple points in the pipeline:

### User Message Filters

- **When**: After preprocessing, before RAG vector search
- **Purpose**: Redact PII from user messages before they're used for vector similarity search
- **Context**: `input.messages[0].role == "user"`

**Impact**: The filtered/modified message is used for:
- RAG vector similarity search
- Subsequent LLM processing
- Chat history storage

### File Content Filters

- **When**: When files are attached to messages
- **Purpose**: Filter sensitive content from uploaded files before indexing
- **Context**: `input.context.file_ref` contains the file reference

### Tool Response Filters

- **When**: After a tool returns data, before sending to LLM
- **Purpose**: Filter sensitive data from external API responses
- **Context**: `input.messages[0].role == "tool"`, `input.context.tool_name` available

## Filters and Proxy Logs

When AI Studio logs request bodies, the proxy log stores the body as it left the request filters. If a filter redacts a prompt, the vendor and the log both get the redacted version.

When a filter blocks a request, the log keeps the original body as the caller sent it. The redactions of earlier filters are not applied to it. If the body contains personal data that the filter must stop, the log contains that personal data.

To keep request and response bodies out of the proxy log for an LLM, turn on **Disable Request/Response Body Logging** on the LLM. An Edge Gateway stores bodies only when [ANALYTICS_STORE_REQUESTS](/ai-management/ai-studio/edge-gateway-env#analytics_store_requests) and [ANALYTICS_STORE_RESPONSES](/ai-management/ai-studio/edge-gateway-env#analytics_store_responses) are on. Both are off by default.
