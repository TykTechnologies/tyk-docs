# Managing Rulesets
 
Create, configure, test, and manage governance rulesets that define the standards your services must meet.
 
## Overview
 
This page covers the practical workflows for managing governance rulesets in Tyk Dashboard: creating new rulesets from templates or your own definition, editing existing ones, testing them against services, deprecating rulesets you no longer need, and managing rulesets programmatically.
 
For the conceptual model behind rulesets, what a rule is, how severity works, and how rulesets are scoped to services through API Categories, see [Core Concepts](/governance/core-concepts).
 
## Quick Start
 
In this tutorial, we'll create a ruleset from the OWASP API Security template and apply it to an API category.
 
### Step-by-Step
 
1. **Open the Rulesets section.** From the left navigation, expand **Governance** and click **Rulesets**. If no rulesets exist yet, the empty state will guide you to create your first one.

   <img src="/img/governance/Ruleset1.png" alt="Governance navigation menu showing the Rulesets section in Tyk Dashboard" />

2. **Create a new ruleset.** Click **+ Create new ruleset**. The three-step creation wizard opens.

   <img src="/img/governance/Ruleset2.png" alt="Rulesets empty state with the Create new ruleset button" />

3. **Add basic info.** Provide a name and description for your ruleset. Link the ruleset to one or more API Categories so it knows which services to evaluate. Set the Deployment Warning toggle (off by default; leave it off to start).

   <img src="/img/governance/Ruleset3.png" alt="Create ruleset wizard - Basic Info step with name, description, categories, and Deployment Warning toggle" />

4. **Choose "Start from template."** This launches the current templates available in your environment.

   <img src="/img/governance/Ruleset4.png" alt="Create ruleset wizard - choosing a starting point" />

5. **Select a template.** For this tutorial, choose **OWASP API Security** for security baseline rules. Click **Continue**.

   <img src="/img/governance/Ruleset5.png" alt="Create ruleset wizard - template selection" />

6. **Review and edit the template definition.** The selected template's JSON is loaded into the Monaco editor. You can disable individual rules, adjust severities, or modify rule definitions before continuing.

   <img src="/img/governance/Ruleset6.png" alt="Create ruleset wizard - raw definition editor showing the selected template's JSON" />

7. **Click Save.** There are 2 options: **Save as draft** (save without activating; does not evaluate APIs) and **Save and activate** (evaluate all mapped APIs). Click **Save and activate**. The ruleset is now created. You are redirected to its detail page, where you can verify the configuration and run a test against any service.

   <img src="/img/governance/Ruleset7.png" alt="Ruleset detail page after creation, showing configuration and test panel" />

### Validation
 
- The new ruleset appears in the Rulesets list with status **Active**.
- Services tagged with the linked categories will begin to be evaluated against the ruleset in the background.
- After async background evaluation is complete, the Governance tab for any matching service now shows results from this ruleset.
## Managing Rulesets
 
### Finding rulesets in the list
 
The Rulesets list page shows every ruleset in your organization. Use the search bar to filter by name and the category dropdown to filter by API Category.
 
The list shows, for each ruleset:
 
- **Status**: Active or Inactive icon. Inactive rulesets do not evaluate services.
- **Name**: Click to open the ruleset's detail page.
- **Category**: The API Categories the ruleset is linked to.
- **Deployment Warning**: Depending if the warning toggle is on or off. See [Core Concepts – Deployment Warning](/governance/core-concepts#deployment-warning).
- **Last updated**: When the ruleset was most recently modified.
- **Actions**: To view or edit each ruleset.
<img src="/img/governance/Ruleset8.png" alt="Rulesets list showing status, name, category, deployment warning, and last updated columns" />

### Creating a ruleset
 
Tyk Governance offers two paths for creating a ruleset, both accessed through the **+ Create new ruleset** wizard.
 
Once a ruleset is linked to a category, you can also run it against an API definition from your CI/CD pipeline before that API is ever imported. See [CI/CD Integration](/governance/cicd-integration).
 
#### From a template
 
Templates are pre-built rulesets. They give teams a runnable starting point on day one, rather than requiring rules to be authored from scratch. The wizard takes you through:
 
1. **Define basic information**: Name, description, Deployment Warning toggle, and API Categories.
2. **Choose starting point**: Select **Start from template**.
3. **Browse templates**: Choose between the current available templates.
4. **Review and edit**: The template's JSON is loaded into the editor. Adjust as needed.
For a guided tutorial with screenshots on how to create a ruleset with a template, see [Quick Start](#quick-start) above.
 
#### From your own definition
 
If you already maintain Spectral rulesets, or you want to write one from scratch, choose **Start with your own definition**.
 
You then have two sub-options:
 
- **Import from file.** Upload a `.json` or `.yaml` Spectral-compatible ruleset.

  <img src="/img/governance/Ruleset9.png" alt="Provide your ruleset definition - import from file" />

- **Paste ruleset definition.** Paste or write the ruleset directly into the Monaco editor.

  <img src="/img/governance/Ruleset10.png" alt="Provide your ruleset definition - paste ruleset definition in the Monaco editor" />

### Configuring an existing ruleset
 
Click any ruleset in the list to open its detail page, and click **Edit**, or select **Edit** from the Actions drop-down. The page has two tabs.
 
#### Basic configs
 
The default tab. From here you can adjust:
 
- **Status**: Inactive (does not evaluate services) or Active (evaluates all mapped services).
- **Name**: Required, unique within the organization.
- **Description**: Long-form description.
- **Link ruleset to services (Category)**: Multi-select. The ruleset will evaluate services in any of the selected categories.
- **Deployment Warning toggle**: Off by default. When on, saving a non-compliant service in a matching category produces a soft warning at deploy time.
<img src="/img/governance/Ruleset11.png" alt="Ruleset edit page - Basic configs tab" />

#### Raw definition
 
The Raw definition tab exposes the full ruleset JSON in a Monaco editor. Use this tab to edit individual rules, change severities, adjust JSONPath selectors, edit `howToFix` text, or add and remove rules.
 
<img src="/img/governance/Ruleset12.png" alt="Ruleset edit page - Raw definition tab showing the full ruleset JSON" />

When you save changes on either tab, all services governed by this ruleset are re-evaluated automatically in the background.
 
### Testing a ruleset against a Service
 
Every ruleset detail page includes a Test ruleset panel. Use it to preview how the ruleset would behave against a specific service, without affecting that service's compliance status.
 
To run a test:
 
<img src="/img/governance/Ruleset13.png" alt="Ruleset detail page showing the Test ruleset panel" />

1. Open the ruleset's detail page.
2. In the Test ruleset panel, select a service from the dropdown.
3. Click **Run ruleset**.
4. Review the issues returned, graded by severity (Error, Warn, Info).

<img src="/img/governance/Ruleset14.png" alt="Test ruleset panel showing results graded by severity after running a test" />

Test results are informational only. They are not stored, do not appear on the service's Governance tab compliance summary, and do not trigger background re-evaluation. Tests are useful for:
 
- Reviewing how a ruleset will affect services before activating it.
- Iterating on rule severity or rule definitions while editing the Raw definition.
- Spot-checking an individual service against a ruleset that isn't currently linked to its category.

### Delete a ruleset
 
To delete a ruleset, click on **Edit Ruleset**, and a new button on the top right will appear to delete the ruleset. Afterwards, a confirmation modal opens, confirming the deletion.
 
## Templates
 
Tyk Governance ships with two templates that cover some common starting points for API governance. Templates are pre-configured rulesets that you can use directly or customize before saving as your own ruleset.
 
| Template | Focus | When to Use |
|---|---|---|
| OWASP API Security | Security baseline rules aligned with the OWASP API Security Top 10 | Establishing security standards for customer-facing or externally-exposed APIs |
| Vacuum-Recommended | OpenAPI design best practices — naming conventions, documentation completeness, response definitions, operation IDs | Establishing baseline design quality and consistency across the API portfolio |
 
You can also import any existing Spectral ruleset through the own-definition flow. The Vacuum engine that executes rulesets is fully compatible with the Spectral ruleset format, so existing rulesets work without modification.
 
## Best Practices
 
- **Start with templates.** The OWASP API Security and Vacuum-Recommended templates cover most baseline cases without requiring custom authoring.
- **Use clear, actionable `howToFix` text.** When a rule fires, the API owner should be able to act on the guidance immediately.
- **Keep rulesets focused.** A ruleset of 200 mixed-purpose rules is harder to maintain than three rulesets of 60 each, organized by domain (security, design, documentation).
- **Use the test sandbox before activating.** This is a useful tool to run a draft ruleset against representative services before linking it to live categories, especially when promoting rules to Error severity.
- **Assign clear ownership.** Document which team or individual owns each ruleset, so changes go through a sensible review.
## FAQ
 
- **What's the difference between starting from a template vs. writing my own?** - Governance ships with two curated templates: OWASP API Security and OAS/OpenAPI design standards, giving you a ready-to-use starting point you can customize. Writing your own ruleset from scratch, or importing an existing Spectral ruleset, gives you full control when your standards don't map closely to either template.
- **Is there a limit to how many rules a ruleset can contain?** - No, there is no limit.
- **If I edit a ruleset, does every service it governs get re-evaluated automatically?** - Yes. Editing a ruleset automatically triggers re-evaluation of every API it governs via linked categories, not something you need to trigger manually.
- **Is there a limit on how many rulesets or categories a service can contain?** - There's no limit on how many rulesets can govern a single service; an API can be linked to any number of rulesets at once. The only "20" limit that exists is on the CI/CD Sandbox API specifically: a single call there supports up to 20 categories, and category-based resolution is capped at 20 resolved rulesets (returns a 400 if exceeded). That cap applies only to the Sandbox API call, not to the Dashboard.
- **Are changes to rulesets audited?** - Yes. Creating, editing, and deleting rulesets are all recorded in Tyk Dashboard's existing audit log.
