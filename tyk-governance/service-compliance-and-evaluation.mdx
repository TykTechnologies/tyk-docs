# Service Compliance and Evaluation
 
## Overview
 
Service Compliance and Evaluation is the API-owner-facing side of Tyk Governance. While [Managing Rulesets](https://tyk.io/docs/tyk-governance/managing-rulesets) covers how governance owners define standards, this page covers how API owners see, understand, and act on those standards from inside the service configuration view.
 
Tyk Governance surfaces compliance information in two main places: the API list, which gives a portfolio-level view across all services, and the Governance tab on each individual service, which gathers the detailed per-service picture in one place.
 
## Quick Start
 
In this tutorial, we'll review the compliance status of an existing service and resolve a non-compliant issue.
 
### Step-by-Step
 
1. **Open the Service.** From the Tyk Dashboard, navigate to APIs and open the service you want to review. The API Designer opens.

<img src="/img/governance/Evaluation1.png" alt="API List" />

2. **Switch to the Governance tab.** The tab appears as the last tab in the API details page, marked with a **New!** badge.

<img src="/img/governance/Evaluation2.png" alt="Governance TAB" />

3. **Read the status banner.** The top of the tab shows the service's overall compliance status: Compliant (no Error-severity issues) or Non-compliant (at least one Error-severity issue), with a count of warnings and errors aggregated across all rulesets evaluating this service.

4. **Review the rulesets.** The Rulesets card grid shows every ruleset evaluating this service, with the per-ruleset compliance status, error, and warning counts.

5. **Open the Issues table.** Below the cards, the Issues table lists each individual rule failure. Use the severity pills (All issues / Errors / Warnings) and the dropdown filters (by ruleset, by remediation priority) to focus on what you want to address.

<img src="/img/governance/Evaluation3.png" alt="Governance TAB Issues" />


6. **View an issue.** Click the **View issue** action on any row to open the issue details.

<img src="/img/governance/Evaluation4.png" alt="Issue Details" />

7. **Read the remediation guidance.** Each issue shows the rule that failed, the affected area in the service specification, the problem if not fixed, and concrete "How to fix" guidance. The platform engineer should provide this information when creating the ruleset.

8. **Apply the fix.** Switch to the relevant tab in the API Designer (Settings, Endpoints, etc.) and update the service to address the issue.

9. **Save the Service.** Saving triggers a re-evaluation (if the service is in Active mode). The Governance tab updates with the new status, typically within seconds.

## Working with the Governance Tab
 
The Governance tab is organized into four sections, top to bottom: the status banner, the rulesets card grid, the issues table, and the test panel. This section covers each in detail.
 
### Governance status banner
 
A full-width card at the top of the tab summarising the service's overall compliance posture.
 
- **Status icon and label.** Compliant (green) if the service has zero Error-severity issues across all applicable rulesets; Non-compliant (red) if any Error-severity issue exists; an amber warning state if the evaluation is in progress.
- **Errors count.** The number of Error-severity issues across all rulesets evaluating this service. Errors are the issues that affect compliance status.
- **Warnings count.** The number of Warn-severity issues across all rulesets. Warnings are advisory and do not change compliance status.
The banner reflects the current state of compliance. It updates automatically when the service changes, when a ruleset changes, or when API Categories are updated.
 
<img src="/img/governance/Evaluation5.png" alt="Governance Status Banner" />
 
### Rulesets associated with this Service
 
A card grid showing every ruleset evaluating this service. Each card represents one ruleset, identified through API Category match (see [Core Concepts → API Categories](https://tyk.io/docs/tyk-governance/core-concepts#api-categories) for how scoping works).
 
Each card shows:
 
- **Status badge.** Compliant or Non-compliant for this ruleset against this service.
- **Ruleset name.** Click to navigate to the ruleset's detail page.
- **Errors count.** Number of Error-severity issues this ruleset detected on this service.
- **Warnings count.** Number of warning-severity issues this ruleset detected on this service.
The grid is paginated at 6 cards per page. If a service is governed by many rulesets, additional pages of cards become available.
 
<img src="/img/governance/Evaluation6.png" alt="Ruleset Card Grid" />
 
### Issues for this Service
 
A filterable, paginated table of every individual issue detected against this service across all evaluating rulesets.
 
**Filters**
 
- **Severity pills (left).** Toggle between All issues, Errors, and Warnings. Each pill shows a count.
- **Filter by ruleset (right).** Restrict the table to issues from a single ruleset.
- **Severity.** Restrict the table by priority: Error, Warning, and Info.
**Columns**
 
- **Ruleset**: The ruleset that produced the issue.
- **Rule violated**: The rule identifier (e.g. `authentication_required`). Clickable to view full issue details.
- **Severity**: Badge: Error, Warn, and Info. The column header carries a tooltip explaining the difference.
- **Problem if not fixed**: Short description of the risk if the issue is left unresolved.
- **Actions**: A **View issue** button that opens the issue details panel.
<img src="/img/governance/Evaluation7.png" alt="Issues for this API" />
 
### Issue details
 
Clicking **View issue** on any row opens a detailed panel for that issue.
 
The panel includes:
 
- **The rule that fired**: name, severity, remediation priority.
- **Affected area**: the specific path in the service specification where the rule failed (e.g. `paths./orders.post.security`).
- **Problem if not fixed**: the risk in plain language.
- **How to fix**: concrete remediation guidance authored as part of the rule.
Use the affected-area path to locate the relevant configuration in the API Designer (Settings, Endpoints, Security, etc.) and apply the fix described.
 
<img src="/img/governance/Evaluation8.png" alt="Governance Issue Details" />
 
### Test ruleset against this Service
 
The Test ruleset panel at the bottom of the Governance tab lets you preview how a ruleset would behave against this service, without affecting compliance status. Test runs are sandboxed: results display in the panel but are not saved, do not change the status banner, and do not trigger background re-evaluation.
 
Test runs are useful for:
 
- **Previewing a ruleset before it's linked to your Service.** A platform engineer might publish a new ruleset against a test category first; you can run it against your service to see what it would flag if applied.
- **Spot-checking a specific ruleset.** Even when multiple rulesets evaluate your service, the Test ruleset panel lets you focus on one at a time.
To run a test:
 
1. Select a ruleset from the dropdown.
2. Click **Run ruleset**.
3. Review the test results displayed in the panel, graded by severity, with the same issue details as the live results above.

## The Deployment Warning Flow
 
If any ruleset evaluating a service has its Deployment Warning toggle enabled, saving a non-compliant service produces a soft warning before the service goes live.
 
<img src="/img/governance/Evaluation10.png" alt="Deployment Warning" />
 
The flow:
 
1. The API owner saves a change that would make the service non-compliant (or activates a non-compliant service for the first time).
2. A warning appears stating that this service does not fully meet the compliance requirements.
3. Two options are presented:
   - **Save Anyway**: The save proceeds, the service is activated, and the Governance tab reflects the service state.
   - **View compliance issues**: The save is canceled. The service returns to edit mode so the owner can fix the issues first.
 
When the Deployment Warning toggle is off on every ruleset evaluating the service (the default), no warning appears at save time. The compliance status is still updated and visible in the Governance tab; there is just no interrupting pop-up.

**Note:**
This flow covers saving from the Dashboard. If your team also gates deployments through Tyk Operator, that check runs independently and can be configured to block, regardless of what happens here.

## What to Expect: Evaluation Performance
 
Evaluation runs entirely on the control plane, in the background. It never sits in the path of your API traffic, and it never blocks saving or deploying a service — your Tyk Gateways aren't involved at any point. Evaluation cost is driven by the size of the API definition (mainly its endpoint count), not by traffic volume or by how many rules a ruleset contains.
 
### Typical evaluation times
 
Benchmarked using Tyk's strictest built-in ruleset with every rule enabled; real-world rulesets typically complete faster.
 
| Endpoints in your API definition | Time from save to results |
|---|---|
| 0 – 100 (most APIs) | under 1 second |
| 100 – 200 | ~1 second |
| 200 – 500 | 1 – 5 seconds |
| 500 – 1,000 | a few seconds |
| 1,000+ | up to ~10 seconds |
 
Ruleset size adds negligible overhead — evaluating the same API against rulesets from 5 to 250 rules added roughly half a millisecond of evaluation time per rule. You can apply comprehensive rulesets without a meaningful performance cost.
 
### Keeping evaluation fast
 
- **Keep API definitions modular.** Documents under ~1 MB evaluate fastest; very large monolithic OAS documents are harder to manage generally, and governance follows the same curve.
- **Curate rulesets for signal.** Extra rules cost milliseconds, so the real goal is a findings list your team will act on — start from Tyk's shipped templates and trim to what you enforce.
- **Scope rulesets with categories.** A ruleset re-evaluates every API that shares its categories when it changes, so focused categories keep re-evaluation windows short.
If your API catalog includes many large (1,000+ endpoint) definitions, talk to your Tyk account team about sizing Dashboard memory for your deployment.
 
## Use Cases
 
### Pre-deployment compliance review
 
An API owner is about to activate a new payment API. After setting the API to active and clicking save, a warning pop-up appears stating that the API is not compliant. They switch to the Governance tab and review the compliance picture. The status banner shows two Error-severity issues, both about missing authentication. The owner clicks **View issue** on each, reads the How to fix guidance, adds the missing security configuration in the Settings tab, and saves. Evaluation runs; the API is now compliant and goes live without the Deployment Warning pop-up.
 
### Reviewing the impact of a tightened ruleset
 
A platform engineer has just promoted a documentation rule from Warn to Error severity. APIs that were compliant yesterday may now be non-compliant. As an API owner, you check the API List (filter by the affected Category) or open the Governance tab on your API and see one new Error-severity issue: a missing operation description on a specific endpoint. You add the description, save, and the API is back in compliance.
 
### Dry-running an optional ruleset
 
A new "Tier 1 hardened security" ruleset has been published, but isn't linked to your API's category yet. You want to know what would happen if it were. From the Test ruleset panel, you select the Tier 1 ruleset and click **Run ruleset**. The results show six issues you'd need to address.
 
## FAQs
 
- **Why did my API become non-compliant without me changing anything?** - Because re-evaluation runs whenever a linked ruleset changes, not just when you save the API, your API can become non-compliant (or compliant again) even if you haven't touched it: e.g. a ruleset gains a new rule, a rule's severity changes to Error, or a ruleset is newly applied to your API's category.
- **What's the difference between "Save Anyway" and "View compliance issues"?** - When an API you're saving has compliance issues, you're given two options. Save Anyway saves and deploys the API as-is, despite the issues. View compliance issues cancels the save, returns you to edit mode, and shows the issues so you can review and fix them before saving again.
- **How fast does the Governance tab reflect a fix after I save?** - Most APIs in under 1 second, up to ~10 seconds at 1,000+ endpoints.
