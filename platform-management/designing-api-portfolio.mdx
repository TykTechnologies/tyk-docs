## Introduction

When you have a few APIs, you can configure each one by hand. As the number of APIs grows, this gets harder:

- Every API needs the same baseline, such as authentication, upstream TLS settings and logging. Configuring it by hand for each API takes time and causes mistakes.
- Copies of the same configuration drift apart, so APIs that should behave the same way don't.
- A change to a shared standard, such as a new allowed origin or a stricter rate limit, means editing many APIs. It is also hard to know which APIs to change.
- Different people are responsible for different parts of an API. A platform team owns the standards, and API teams own their APIs.

Tyk Dashboard gives you three tools to manage this. You can use them separately or together:

| Tool | What it does | When it applies |
| :--- | :--- | :--- |
| [API Categories](/platform-management/api-categories) | Groups APIs, for example by team, domain or environment | While the API exists |
| [API Templates](/platform-management/api-templates) | Gives a new API a standard starting point | Once, when you create the API |
| [API Fragments](/platform-management/api-fragments) | Shares configuration that stays linked to every API that uses it | While the API references the Fragment |

## Choosing Between Templates and Fragments

Templates and Fragments both help you reuse configuration. The difference is what happens after you create the API:

- Tyk Dashboard **copies** a Template into a new API. After that, the API and the Template are independent. Use a Template for configuration that each API starts with but can then change, such as default endpoints or a cache configuration that API teams tune.
- An API keeps a **reference** to a Fragment. When you change the Fragment, every API that references it changes too. Use a Fragment for configuration that must stay the same across APIs, such as a security standard.

You get the most value when you combine them. A Template can contain Fragment references. When an API team creates an API from the Template, the new API starts with the standard configuration from the Template. It also stays linked to the Fragments, for the configuration that must not drift. This gives API teams a quick, standard way to create APIs, and gives the platform team one place to change the shared configuration.

## Common Uses for Fragments

A Fragment replaces one value in an API definition, usually a configuration object. These are typical candidates:

| Shared Configuration | Location in the Tyk OAS API Definition |
| :--- | :--- |
| A standard JWT validation setup | An entry in `x-tyk-api-gateway.server.authentication.securitySchemes` |
| Upstream mutual TLS | `x-tyk-api-gateway.upstream.mutualTLS` |
| Upstream TLS settings | `x-tyk-api-gateway.upstream.tlsTransport` |
| A rate limit that protects an upstream service | `x-tyk-api-gateway.upstream.rateLimit` |
| CORS settings for browser clients | `x-tyk-api-gateway.middleware.global.cors` |
| Traffic logging | `x-tyk-api-gateway.middleware.global.trafficLogs` |
| Custom plugin bundle and driver settings | `x-tyk-api-gateway.middleware.global.pluginConfig` |
| IP access control | `x-tyk-api-gateway.server.ipAccessControl` |

A Fragment can also hold part of the OpenAPI description, for example a security scheme that many APIs share.

Don't use a Fragment for:

- configuration that is specific to one API, such as its listen path or upstream URL
- configuration that you expect API teams to change for their API. Put it in a Template instead.
- settings that Tyk Developer Portal writes to the API, if the Developer Portal publishes the API. See the [limitations of API Fragments](/platform-management/api-fragments#limitations).

## Sharing Ownership Between Teams

Templates and Fragments let you split the responsibility for an API between teams:

- The **platform team** owns the Templates and Fragments. It decides the standard configuration, and changes it in one place.
- **API teams** own their APIs. They create APIs from the Templates, and change the parts of their APIs that the Fragments don't set. In the API Designer, settings from a Fragment show the **Shared configuration** badge, and API teams can't change them in the API.

Use [user permissions](/platform-management/user-permissions) to enforce this split. Give the platform team write access to the `api_assets` permission, which controls Templates and Fragments. Give API teams write access to the `apis` permission, and read access to `api_assets` so that they can use the Templates.

<Warning>
A user who can change a Fragment can change every API that references it. Give write access to `api_assets` only to users that you trust to change all of these APIs.
</Warning>

Use [API ownership](/platform-management/api-ownership) to give each API team access to only its own APIs, and [API Categories](/platform-management/api-categories) to group them.

## Changing Shared Configuration Safely

A change to a Fragment applies to every API that references it, so plan it as you would a change to all of those APIs:

1. Open the Fragment and check **APIs using this fragment** to see which APIs the change affects.
2. Make the change in a test environment first.
3. Save the change. Before Tyk Dashboard saves it, it validates every API and Template that references the Fragment. If any of them would no longer be valid, Tyk Dashboard rejects the change and lists the APIs that would break. A change that makes an API definition invalid therefore can't reach Tyk Gateway.

## Designing Standards In and Checking for Them

Templates and Fragments build your standards into APIs when you create them. [Tyk Governance](/tyk-governance/overview), a licensed capability of Tyk Dashboard, checks APIs against your standards, and reports the APIs that don't meet them. The two work together:

- Use Templates and Fragments so that new APIs meet your standards from the start.
- Use Governance rulesets to find existing APIs that don't meet your standards, and to catch changes that break them.

Tyk Governance evaluates each API with its Fragment references resolved, so configuration that comes from a Fragment counts towards compliance. When you change a Fragment, Tyk Governance evaluates the APIs that reference it again. You can also use API Categories to choose which APIs a ruleset applies to. See [Scoping Rulesets](/tyk-governance/scoping-rulesets).
